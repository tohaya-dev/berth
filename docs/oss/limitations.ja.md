# 既知の制限事項

このリリースの Berth でできないこと、または一部しかできないことをまとめます。各項目の根拠は、同梱のスクリプト、マニフェスト、アプリケーションコードです。ホストの必要スペックは[動作要件](requirements.ja.md)を、具体的な症状への対処は[トラブルシューティング](troubleshooting.ja.md)を参照してください。

## 対応プラットフォーム

- **Linux x86_64 のみ対応です。** `deploy/k8s/linux/install-k3s.sh` はそれ以外のアーキテクチャでは停止します。ビルドと受け入れ試験を済ませたのも amd64 イメージだけです。このリリースは macOS、arm64、Windows ネイティブコンテナに対応していません。
- **動作確認済みの環境は Windows 11 + WSL2 Ubuntu 24.04 です。** ネイティブの Ubuntu 24.04 でも同じアダプターを使えますが、実機での受け入れ試験は未了です。Ubuntu 22.04 は試験していません。Windows ホストの再起動も未試験です([Windows ランチャー](windows-launcher.ja.md)を参照)。
- **systemd と、パスワード入力なしの sudo が必要です。** インストーラーは PID 1 が systemd であることを確認し、`sudo -n true` を実行します。
- **K3s は 1 ディストリビューションにつき 1 つだけです。** `/usr/local/bin/k3s` や `k3s*` という名前の systemd ユニットが既にあると、インストーラーは実行を拒否します。他のクラスターを再利用したり上書きしたりすることはありません。
- **シングルノード構成です。** モデルと取り込み文書はノード上の `hostPath` ボリュームで、PostgreSQL と Redis は K3s の local-path ストレージを使います。マルチノードのクラスターは検証していません。

## 可用性(冗長化されていない部分)

- PostgreSQL + pgvector と Redis は、それぞれ `Recreate` 戦略の **1 レプリカ** で動きます。どちらかの Pod が再起動すると、戻るまでアプリケーションは使えません。
- API と worker は同じノード上でそれぞれ 2 レプリカ動きます。ローリング再起動はできますが、ノード、WSL ディストリビューション、Windows ホストの障害には耐えられません。
- `ops/linux.sh stop` はアプリケーション、Redis、PostgreSQL を 0 台にスケールします。K3s 自体は動き続けます。
- 入口は `kubectl port-forward` です。`connect` は接続先の Pod が終了すると終わるので、起動し直す必要があります。`serve`(Windows ランチャーが使います)は自動で再接続を繰り返します。WSL2 では、Windows 側で WSL クライアントが動いている間しかディストリビューションが起動し続けません。その役割をランチャーが担います。
- `wsl --terminate` の後、試験に使った cgroup v1 のホストではコールドリカバリーに最大 15 分かかりました。

## リソース

- API Pod はそれぞれメモリ要求 2Gi・上限 6Gi、worker Pod はそれぞれ要求 768Mi・上限 6Gi です。PostgreSQL と Redis には要求も上限もありません。CPU の上限はありません。詳細と合計は[動作要件](requirements.ja.md)にあります。
- メモリ使用量を抑えるため、レンダラーは `masking.parallelism = 1` と `worker.embedding_mode = minimal` を固定で設定します。マスキングは 1 件ずつ実行されるので、大量の取り込みには時間がかかります。
- PostgreSQL ボリュームの要求サイズは 2Gi、Redis ボリュームは 1Gi です。

## モデルとネットワーク

- **モデルはインストール前にダウンロードしておく必要があります。** `tools/download-rag-models.py` が、固定した埋め込みモデルとリランカーモデルを Hugging Face から `$BERTH_DATA_DIR/models` に取得します。イメージは `HF_HUB_OFFLINE=1` と `TRANSFORMERS_OFFLINE=1` を設定して動きます。Pod はモデルディレクトリを読み取り専用でマウントし、モデルを一切ダウンロードしないので、足りないモデルを実行中に取りに行くことはできません。[モデルポリシー](model-policy.ja.md)を参照してください。
- **インストールにはインターネット接続が必要です。** 接続先は K3s インストーラー(`get.k3s.io`)、Hugging Face、イメージビルドで使うもの(ベースイメージ、Debian パッケージ、PyPI、PyTorch CPU 版の配布元、spaCy モデルの wheel)、それに `pgvector/pgvector:pg16` と `redis:7.2-alpine` のイメージです。
- **回答生成用のモデルは含まれていません。** 新規インストール直後は到達できないループバックのエンドポイントを指しているので、外部プロバイダーを設定するまでチャットはプロバイダーエラーを返します。プロバイダーを設定すると、検索で取り出した文書テキストがそこへ送られます。リモートのプロバイダーなら、そのテキストはマシンの外へ出ます。
- **CPU のみで動きます。** イメージには PyTorch の CPU 版が入っていて、マニフェストは GPU を要求しません。

## 取り込める形式と制限

文書は `$BERTH_DATA_DIR/ingest` 配下のフォルダーからだけ取り込まれます。Pod はこのフォルダーを読み取り専用でマウントします。元文書をブラウザーからアップロードする機能はありません。このフォルダー内のシンボリックリンクはたどられ、コンテナの中で解決されます。リンクは置かないでください。

| 形式 | 拡張子 | 制限 |
|---|---|---|
| テキスト | `.txt` `.md` | UTF-8 として読みます。解釈できないバイトは捨てられます |
| CSV | `.csv` | **先頭 50 行だけ**を索引に入れます(読み込むのは最大 10,000 行) |
| PDF | `.pdf` | 既定の「fast」モードはテキストレイヤーだけを読みます。**テキストレイヤーのないスキャン PDF からは文字が取れません。**「vision」モードには画像を扱えるモデルのエンドポイントが必要です |
| Word | `.docx` | 段落と表を読みます。旧形式の `.doc` には**対応していません** |
| PowerPoint | `.pptx` | スライドの文字とノートを読みます。旧形式の `.ppt` には対応していません |
| Excel | `.xlsx` | 100 行を超えるシートは**先頭 50 行**だけを索引に入れます。`.xls` は拡張子としては受け付けますが、`.xlsx` 用の読み込み処理で開くため旧来のバイナリ形式は読めません。`.xlsx` に変換してください |
| HTML・メール | `.html` `.htm` `.eml` | 文字だけを読みます。スクリプトとスタイルは除きます |
| ZIP | `.zip` | 中の対応ファイルを 1 階層だけ展開します。入れ子のアーカイブは飛ばします |
| 画像 | `.jpg` `.jpeg` `.png` `.heic` `.webp` `.gif` | 既定では**ファイル名だけ**を索引に入れます。画像の説明文を作るには `image.processing_mode = lm_studio` と、画像を扱えるエンドポイントが必要です。リモートの画像エンドポイントは `allow_remote_vlm` を設定しない限りブロックされます。`caption` モードは Apple silicon 用のライブラリを使うので、この Linux イメージでは使えません |

これ以外の拡張子は非対応として飛ばします。スキャン処理にはファイルごとのサイズ上限も抽出のタイムアウトもありません。非常に大きなファイルは必要なだけ時間がかかり(停止要求は受け付けます)、worker のメモリを上限 6Gi の範囲で使います。

## マスキングと個人情報

- 検出には Microsoft Presidio と spaCy モデル `en_core_web_sm` / `ja_core_news_sm` を使います。`lite` モードで対象になるのはメールアドレス、電話番号、日時です。`standard` と `quality` では、日本語の人名、組織名、地名、住所が加わります。Presidio を読み込めない場合は正規表現にフォールバックし、メール、電話番号、IP アドレス、カード番号らしき数字、12 桁の番号らしき数字、内部 URL を検出します。検出は統計的な推定とパターン照合によるものです。**個人情報を見落とすことも、個人情報でない文字列をマスクすることもあります。** マスキングを保証とみなさないでください。
- モードの値(`lite`、`standard`、`quality`)は `cynovela.yaml` の `pii_mode` から読みます(既定は `standard`)。Kubernetes ではこのファイルが ConfigMap からマウントされます。設定画面で変更しても、反映されるのはそのリクエストを処理した API プロセスだけで、保存はされません(応答に `yaml_persisted: false` が返ります)。恒久的に変えるには、リポジトリの `cynovela.yaml` の `pii_mode` を編集して `./ops/linux.sh start` を実行してください。ConfigMap が作り直されます。

## 認証とアクセス制御

- ロールは `admin` と `viewer` の 2 つです。これにワークスペース/コレクション単位のアクセス規則と、CLI・HTTP MCP 用のスコープ付き API キーが加わります。
- 新規インストールでは管理者 `cynovela` が 1 人だけ作られ、パスワードは自動生成されます(`$BERTH_DATA_DIR/secrets/admin_password`)。初回ログイン時の変更は強制されません。
- パスワードは PBKDF2-HMAC-SHA256(反復 100,000 回)でハッシュ化されます。これは PBKDF2 に関する現在の OWASP の推奨値を下回ります。
- ログイントークンは JWT で、既定の有効期間は 8 時間です。ログイン、トークンの更新、パスワード変更、パスワード確認は、それぞれ接続元アドレスと API Pod ごとに毎分 5 リクエストに制限されます。それ以外のエンドポイントに回数制限はありません。既定の `kubectl port-forward` の入口では、すべてのクライアントがループバックアドレスから Pod に届くため、この制限を全員で共有します(ログインの失敗を繰り返すと、1 分間は全員がログインできなくなることがあります)。監査記録の接続元アドレスも `127.0.0.1` になります。
- 管理者がパスワードを再設定しても、利用者に新しいパスワードの変更は強制されません。API キーに有効期限はありません。不要になったキーは失効させてください。
- LLM の API キーがデータベースに暗号化して保存されるのは、`openai_compat` プロバイダーの場合だけです。ほかのプロバイダーでは、設定画面で入力したキーはそれを受け取った API Pod のメモリにだけ保持されます。もう 1 つの API レプリカとは共有されず、その Pod が再起動すると消えます。

## バックアップと復元

- `ops/linux.sh backup` がダンプするのは **PostgreSQL データベースだけ**(リレーショナルデータとベクトル)で、対になる `secret_key` もコピーします。モデル、取り込んだ元ファイル、Redis のキュー、ほかの秘密ファイル、レンダリング済みマニフェストは**含まれません**。
- ダンプは暗号化されていません。保存されている文書テキストを復号できる鍵のコピーと同じ場所に置かれるので、バックアップ先のディレクトリはそれに見合った保護をしてください。
- 定期バックアップの仕組みはありません。`PG_BACKUP_DIR` を指定しない場合、ダンプは `$HOME/dt-backups/k8s-pg` に書かれます。
- `restore DUMP --yes` は、復元先の鍵がバックアップの鍵と一致することを確認します。API と worker は事前に自分で 0 台にスケールしておく必要があります。[Linux / WSL2 ガイド](linux-wsl.ja.md#運用と復旧)を参照してください。
- API/worker のコンテナレイヤーにあるアプリケーションログなどの実行時ファイルは、Pod が入れ替わると失われます。Pod があるうちに `kubectl logs` で確認してください。

## ネットワークへの公開

- 入口の port-forward は既定で `127.0.0.1:18765` にバインドします。`BERTH_ENTRY_ADDRESS`(または `$BERTH_DATA_DIR/entry-address`)で公開範囲を広げられますが、port-forward 自体は接続元を絞りません。
- K3s の API サーバーは **`0.0.0.0:26443`** で待ち受けます(`--bind-address 0.0.0.0`)。他のマシンから届くかどうかは、WSL のネットワークモードとファイアウォール次第です。ホストとネットワークの両面で保護してください。K3s はこれ以外にもノードのポートを開きます。
- アプリケーションの Service は `ClusterIP` です。Kubernetes の NetworkPolicy は生成されません。

## 運用

- **アンインストール用のコマンドはありません。** 削除は手作業です。[アンインストールとアップグレード](uninstall-upgrade.ja.md)を参照してください。
- `ops/linux.sh` はインストールした名前空間を記憶しません。`BERTH_NAMESPACE`(既定値 `berth`)を使います。別の名前空間にインストールした場合は、どのシェルでも `BERTH_NAMESPACE` を export してください。忘れると、別の(空の)名前空間に対してコマンドが実行されます。
- API と worker の Pod には、マニフェストで `TZ=Asia/Tokyo` が設定されています。
- 一部の Kubernetes オブジェクトは以前の名前のままです。Deployment の `cynovela`、`cynovela-worker`、`cynovela-pgvector`、`cynovela-redis`、Service の `cynovela-svc`、Secret の `cynovela-secret`、ブートストラップ Job の `hansolo-bootstrap` です。

## 旧名称へのフォールバック

旧名称で作ったインストールを動かし続けるための仕組みです。将来削除されることがあります。

- `HAN_SOLO_*` 環境変数は、`BERTH_*` の非推奨の別名として受け付けます。両方あれば `BERTH_*` が優先されます。
- `BERTH_DATA_DIR` も `HAN_SOLO_DATA_DIR` も設定されておらず、`~/.local/share/berth` もない場合、`~/.local/share/hansolo` があれば `ops/linux.sh` はそちらを使い、通知を表示します。
- インストーラーはコンテキスト名として `berth-*` のほかに `hansolo-*` も受け付けます。
- Windows ランチャーは `%LOCALAPPDATA%\HanSolo\<context>` の状態を `%LOCALAPPDATA%\Berth\<context>` へ 1 回コピーします。古いディレクトリは残します。
- ソースツリーにはスタンドアロン用の経路(`cynovela.yaml` の SQLite/Chroma の既定値)がまだ残っています。Kubernetes 用のレンダラーがこれを PostgreSQL/pgvector と Redis で上書きするので、現在の Berth の構成としては使われません。
